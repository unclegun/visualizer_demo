HTMX Spike for .NET Core Razor Pages

Architecture and implementation spike for server-rendered applications using Razor Pages, PageModel handlers, and a DAL-first data access structure without MVC controller dependency.

Executive summary

HTMX is an HTML-centric interaction library where elements issue HTTP requests using attributes and update page fragments from server-returned HTML. It is a practical fit for Razor Pages because handlers already return partial markup and server-side validation/state remains authoritative.

Recommendation: Recommended for selective adoption in CRUD-heavy and form-heavy server-rendered screens.

How HTMX works

hx-get + hx-target

Fetch HTML from a handler and place it in a specific fragment container.

<button
  hx-get="/Users?handler=Search&term=ali"
  hx-target="#results"
  hx-swap="innerHTML">
  Search
</button>

<div id="results"></div>

hx-post + hx-swap

Submit form fragments to a handler and replace current markup with success/error partial output.

<form
  hx-post="/Users?handler=Save"
  hx-target="#editRow-42"
  hx-swap="outerHTML">
  ...
</form>

hx-boost

Upgrade regular links/forms in a section to HTMX-powered requests with minimal markup changes.

<section hx-boost="true" hx-target="#panel">
  <a href="/Users?handler=Page&page=2">Next</a>
</section>

hx-push-url

Keep history and shareable URLs synchronized during fragment navigation.

<input
  name="term"
  hx-get="/Users?handler=Search"
  hx-target="#results"
  hx-push-url="true" />

How it fits our current architecture

Use HTMX at the page edge while keeping orchestration in PageModel handlers and persistence in DAL services. This keeps boundaries clear and avoids leaking UI transport concerns into data access logic.

Request flow

  1. 1. User action on an element with hx-* attributes.
  2. 2. Request hits a Razor Page handler (OnGet/OnPost handler).
  3. 3. PageModel calls DAL and maps result to a view model.
  4. 4. Server returns HTML fragment from a partial Razor view.
  5. 5. HTMX swaps fragment into the target DOM element.

Pros / Cons comparison

Pros

  • Fits Razor Pages handler model naturally.
  • Less custom JavaScript for common interactions.
  • No SPA framework required for most CRUD screens.
  • Incremental adoption by page, panel, or control.
  • Server remains source of truth for UI state.
  • Strong fit for forms, modals, tables, and filters.

Cons

  • Requires disciplined partial layout and naming.
  • Can become hard to reason about if overused.
  • Weak fit for rich client-state-heavy experiences.
  • DOM swaps may require widget re-initialization hooks.
  • Team conventions are mandatory to avoid drift.

Best-fit and poor-fit use cases

Best-fit

  • Inline edit of table rows.
  • Modal content loading and post-submit refresh.
  • Search, filter, and paging fragments.
  • Dependent dropdowns and server-validated options.
  • Partial form save workflows.
  • Approval panels and status checkpoints.
  • Status refresh and lightweight polling.

Poor-fit

  • Complex drag/drop builders with deep transient state.
  • Canvas-heavy interactive interfaces.
  • Rich charting applications with deep client state.
  • Full offline-first applications.

Index.cshtml.csPageModel Handlers
public class IndexModel : PageModel
{
    private readonly IUserDal _userDal;

    public IReadOnlyList<UserRowVm> Users { get; private set; } = [];

    public IndexModel(IUserDal userDal) => _userDal = userDal;

    public async Task OnGetAsync()
    {
        Users = await _userDal.GetUsersAsync();
    }

    public async Task<PartialViewResult> OnGetEditRowAsync(int id)
    {
        var user = await _userDal.GetUserAsync(id);
        return Partial("_EditUserRow", new EditUserVm(user));
    }

    public async Task<PartialViewResult> OnPostSaveRowAsync(EditUserVm input)
    {
        if (!ModelState.IsValid)
        {
            return Partial("_EditUserRow", input);
        }

        await _userDal.UpdateUserAsync(input.ToCommand());
        var updated = await _userDal.GetUserAsync(input.Id);
        return Partial("_UserRow", new UserRowVm(updated));
    }

    public async Task<PartialViewResult> OnGetRowAsync(int id)
    {
        var user = await _userDal.GetUserAsync(id);
        return Partial("_UserRow", new UserRowVm(user));
    }

    private PartialViewResult Partial(string name, object model)
        => new()
        {
            ViewName = name,
            ViewData = new ViewDataDictionary(ViewData, model)
        };
}

Team conventions / recommended standards

  • Use HTMX for HTML fragment flows, not JSON-first UI orchestration.
  • Keep DAL contracts and service boundaries unchanged.
  • Keep interaction orchestration in PageModel handlers.
  • Use explicit partial names that match handler intent.
  • Prefer localized HTMX usage over page-wide blanket usage.
  • Maintain full-page fallback where practical.

Acceptance criteria

  • POC demonstrates at least three HTMX flows in Razor Pages.
  • Handlers call DAL without introducing controller abstractions.
  • Validation failures return partials with clear UX behavior.
  • Standards document approved by engineering leads.

Copyable developer explanation

Meeting script

HTMX is a strong selective fit for our Razor Pages stack because it lets us improve interaction speed without replacing our architecture. We keep routing and orchestration in PageModel handlers, keep DAL boundaries intact, and return partial Razor fragments as the UI contract. The result is less custom JavaScript for CRUD-heavy workflows, while still preserving server-side validation and maintainability. We should adopt HTMX where it clearly improves forms, tables, and modals, and avoid using it as a blanket solution for highly stateful client applications.

Adoption plan

Phase Objective Output
Phase 1: Pilot Apply HTMX to one high-value CRUD/form page. Measured latency and implementation notes.
Phase 2: Conventions Codify partial/handler standards and review checklist. Shared internal standards reference.
Phase 3: Rollout Expand to adjacent screens where HTMX is a clear fit. Controlled adoption with architecture guardrails.

Final recommendation

HTMX is a strong selective fit for .NET Core Razor Pages applications that are server-rendered and DAL-driven. It should be adopted intentionally for fragment-oriented CRUD and form workflows, not applied as a universal UI strategy.
