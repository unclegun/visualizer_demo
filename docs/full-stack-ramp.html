Frontend to Full Stack: ASP.NET Core Razor Pages

You already understand the browser and SQL. This course teaches the layer in between: how a request moves from a Razor Page, through a PageModel handler, into a service/DAL, into SQL, and back out as rendered HTML. Six labs, all runnable against the existing reference app.

You Do Not Need to Master These Yet

The goal right now is narrow: safely trace and modify a normal application request from browser to database and back. Everything below is real and useful eventually — just not the bottleneck to being productive on tickets today.

  • Advanced C# language features
  • Advanced LINQ
  • Reflection
  • Middleware internals
  • Microservices
  • Clean Architecture
  • Design-pattern theory
  • Dependency-injection internals
  • Advanced async programming
  • Entity Framework internals

The C# you do need for these labs: classes, properties, methods, basic interfaces, nullable values, collections, async/await at a usage level, simple LINQ (Where, Select, FirstOrDefault), and dependency injection at the "it shows up as a constructor parameter" level. That's it — you'll meet each one inside a lab, not as reading homework.

Core mental model

Every lab traces this same loop. If you can point at each box for a given page, you can handle most tickets.

Browser→ Razor Page (.cshtml)→ PageModel (.cshtml.cs)→ Handler (OnGet / OnPost)→ Service / DAL→ SQL→ Result / model→ Razor / JSON→ Browser

Reference app mapping: Pages/Index.cshtml is the Razor Page, Pages/Index.cshtml.cs is the PageModel, OnGet is the handler, DAL/DataAccess.cs is the DAL, and SQLite (sales.db) is the database.

Labs

Work top to bottom. Each lab is collapsible — expand one at a time and keep the reference app running (dotnet run --project examples/razor-reference/visualizer_demo/visualizer_demo.csproj) alongside your editor.

Lab 1

Trace a Request

Goal

Follow one page load from the browser into C# code and back, without changing behavior yet.

Mental Model

Browser→ Index.cshtml→ IndexModel→ OnGet→ DataAccess

Short Explanation

A Razor Page is two files sharing one name: Index.cshtml (markup, what renders) and Index.cshtml.cs (the PageModel, the C# behind it). The @page directive at the top of the .cshtml marks it as routable; @model IndexModel connects it to its PageModel. When the browser requests the page with a GET, ASP.NET Core calls OnGet on that PageModel before the markup renders.

Relevant Code

// examples/razor-reference/visualizer_demo/Pages/Index.cshtml.cs
public class IndexModel : PageModel
{
    private readonly DataAccess _dataAccess;

    public IndexModel(DataAccess dataAccess)   // <- dependency injection, usage level only
    {
        _dataAccess = dataAccess;
    }

    public ChartData BarData { get; set; }

    public void OnGet()                        // <- runs on every GET request to this page
    {
        BarData = _dataAccess.GetSalesByCategory();
    }
}
// examples/razor-reference/visualizer_demo/Program.cs
builder.Services.AddSingleton<DataAccess>();   // <- makes DataAccess injectable anywhere

The DataAccess constructor parameter on IndexModel is filled in automatically because it was registered in Program.cs. You don't need to know how that wiring works internally — only that "constructor parameter = something the app provides for you."

Run It

  1. Open Pages/Index.cshtml.cs in your editor and locate the IndexModel class.
  2. Set a breakpoint on the first line inside OnGet.
  3. Run dotnet run --project examples/razor-reference/visualizer_demo/visualizer_demo.csproj with the debugger attached (F5 in VS Code, or dotnet watch plus attach).
  4. Load the app's home page in a browser. Confirm the breakpoint hits.
  5. Step into _dataAccess.GetSalesByCategory() and watch it return a populated ChartData.
  6. Step back out and let the page finish rendering. Find where Model.BarData is used in Index.cshtml (via the _ChartPartial partial).

Change It

Add a Console.WriteLine (or a second breakpoint) right where SalesTableData is assigned in OnGet, and confirm it fires on every reload — not just the first one.

Hint

Handlers run fresh on every request. There is no persistent "page instance" between requests the way a SPA component might behave — each GET creates a new IndexModel.

Break It

Temporarily rename OnGet to OnGetX and reload the page.

What happens & why

The page still loads, but BarData and friends are never populated — you'll see empty charts/tables, not an error. Razor Pages falls back to doing nothing if it can't find a matching handler for the verb. This is a common silent-bug shape: markup references a property that was never set. Rename it back when done.

Explain It

In your own words, describe what happens between typing a URL and seeing the sales chart on screen, using the words "PageModel", "handler", and "DAL".

Checkpoint

Lab 2

Read Data

Goal

Follow a SQL SELECT all the way to rendered HTML, and add a new read-only query yourself.

Mental Model

SQL SELECT→ C# object→ PageModel property→ Razor UI

Short Explanation

The DAL runs raw SQL and manually maps each result row onto a plain C# class (a "model"). The PageModel exposes that data as a public property. Razor loops over it with @foreach. There's no magic ORM step here — every column read is explicit, which makes it easy to trace.

Relevant Code

// DAL/DataAccess.cs
public ChartData GetSalesByCategory()
{
    var data = new ChartData();
    using var connection = new SqliteConnection(_connectionString);
    connection.Open();
    var command = connection.CreateCommand();
    command.CommandText = "SELECT Category, SUM(Amount) FROM Sales GROUP BY Category ORDER BY SUM(Amount) DESC";
    using var reader = command.ExecuteReader();
    while (reader.Read())
    {
        data.Labels.Add(reader.GetString(0));   // <- SQL result, column 0
        data.Values.Add(reader.GetDecimal(1));  // <- SQL result, column 1
    }
    return data;                                 // <- C# object
}
// Models/ChartData.cs
public class ChartData
{
    public List<string> Labels { get; set; } = new();
    public List<decimal> Values { get; set; } = new();
}
<!-- Pages/Shared/_ChartPartial.cshtml, table branch -->
@foreach (var row in Model.Data.Item2)
{
    <tr>
        @foreach (var cell in row)
        {
            <td>@cell</td>
        }
    </tr>
}

Run It

  1. Set a breakpoint inside GetSalesTableData() in DataAccess.cs, right after reader.Read().
  2. Reload the home page and inspect reader values per row in the debugger.
  3. Step out to IndexModel.OnGet and watch SalesTableData get assigned.
  4. Find the "Raw Sales Data" card on the rendered page and match a row's values back to what you saw in the debugger.

Change It

Add a new DAL method GetSalesAboveAmount(decimal minimum) that runs SELECT Category, Amount, Date FROM Sales WHERE Amount >= @minimum and returns List<SalesData>. Call it from OnGet, expose it as a new PageModel property, and print the count somewhere on the page (a simple <p> is fine).

Hint
public List<SalesData> GetSalesAboveAmount(decimal minimum)
{
    var sales = new List<SalesData>();
    using var connection = new SqliteConnection(_connectionString);
    connection.Open();
    var command = connection.CreateCommand();
    command.CommandText = "SELECT Category, Amount, Date FROM Sales WHERE Amount >= @minimum";
    command.Parameters.AddWithValue("@minimum", minimum);
    using var reader = command.ExecuteReader();
    while (reader.Read())
    {
        sales.Add(new SalesData
        {
            Category = reader.GetString(0),
            Amount = reader.GetDecimal(1),
            Date = DateTime.Parse(reader.GetString(2))
        });
    }
    return sales;
}

Break It

Swap two column indexes in a reader call (for example read column 1 where column 0 was expected) and reload.

What happens & why

You'll either get a runtime InvalidCastException (types don't line up, like reading a decimal column as a string) or, worse, no exception at all — just wrong data silently rendered. Column-index mapping is a common source of subtle DAL bugs; always double check SELECT column order against your reader.GetX(index) calls.

Explain It

Describe, in order, every hop a single sales row takes from the SQLite file to a table cell on screen.

Lab 3

Send Data Back

Goal

Build a form that submits back to the server, binds to a C# model, and writes to the database.

Mental Model

Form submit→ OnPostAsync→ [BindProperty]→ DAL INSERT→ Redirect / Page()

Short Explanation

A Razor form posts to the same page by default. [BindProperty] tells ASP.NET Core to fill a property from the posted form fields automatically — this is model binding. A named handler like OnPostAsync (or OnPostCreateAsync for multiple forms on one page) runs when that POST arrives. From there you call the DAL to persist the change, then either return RedirectToPage() (typical after a successful save, avoids duplicate submits on refresh) or return Page() (typical when redisplaying the same form, e.g. on validation failure).

Relevant Code

public class AddSaleModel : PageModel
{
    private readonly DataAccess _dataAccess;
    public AddSaleModel(DataAccess dataAccess) => _dataAccess = dataAccess;

    [BindProperty]
    public SalesData NewSale { get; set; } = new();

    public void OnGet() { }

    public async Task<IActionResult> OnPostAsync()
    {
        _dataAccess.InsertSale(NewSale);      // <- new DAL method you write
        return RedirectToPage("./Index");     // <- PRG pattern: redirect after POST
    }
}
<form method="post">
    <input asp-for="NewSale.Category" class="form-control" />
    <input asp-for="NewSale.Amount" class="form-control" />
    <input asp-for="NewSale.Date" class="form-control" />
    <button type="submit" class="btn btn-primary">Save</button>
</form>

There is currently no OnPost handler in Pages/Index.cshtml.cs — that's intentional. You add the first one in this lab.

Run It

  1. Add an InsertSale(SalesData sale) method to DataAccess.cs that runs an INSERT INTO Sales (...) VALUES (...) using parameters (never string-concatenate user input into SQL).
  2. Add a small form to Index.cshtml (or a new page) with [BindProperty] and an OnPostAsync handler that calls it.
  3. Set a breakpoint in OnPostAsync, submit the form, and inspect the bound values.
  4. Confirm the new row appears after redirect by re-running your Lab 2 read query.

Change It

Add a second, named handler OnPostDeleteAsync(int id) on the same page, wired to a per-row delete button (asp-page-handler="Delete"), and a matching DAL DeleteSale(int id).

Hint
<form method="post" asp-page-handler="Delete" asp-route-id="@row.Id">
    <button type="submit" class="btn btn-outline-danger btn-sm">Delete</button>
</form>

A handler named OnPostDeleteAsync is invoked by posting with ?handler=Delete, which asp-page-handler="Delete" generates for you.

Break It

Remove [BindProperty] from NewSale and resubmit the form.

What happens & why

The form still posts successfully, but NewSale stays at its default (empty) values inside the handler — nothing binds the posted fields to it. No exception, just quietly wrong data, which is why Lab 4 pairs validation with debugging: you need to be able to notice this instead of assuming binding "just works".

Explain It

Explain what [BindProperty] does, and why RedirectToPage is usually preferred over return Page() immediately after a successful save.

Lab 4

Validation and Debugging

Goal

Reject bad input safely, and get comfortable diagnosing a failed request with the debugger instead of guessing.

Mental Model

Data annotations→ ModelState→ IsValid check→ return Page()

Short Explanation

Data annotations like [Required] or [StringLength] are attributes on model properties. When a form posts, ASP.NET Core checks them automatically and records failures in ModelState. Your handler must explicitly check if (!ModelState.IsValid) return Page(); — nothing stops execution for you. On the exception side: an uncaught exception in a handler shows a developer error page locally with a full call stack; use breakpoints and the call stack panel to find where it actually originated, not just where it surfaced.

Relevant Code

public class SalesData
{
    [Required]
    public string Category { get; set; }

    [Range(0.01, 1_000_000)]
    public decimal Amount { get; set; }

    public DateTime Date { get; set; }
}
public async Task<IActionResult> OnPostAsync()
{
    if (!ModelState.IsValid)
    {
        return Page();               // <- redisplay form with validation messages
    }

    _dataAccess.InsertSale(NewSale);
    return RedirectToPage("./Index");
}
<span asp-validation-for="NewSale.Category" class="text-danger"></span>

Run It

  1. Add [Required] to Category on SalesData (or your own model from Lab 3) and add the ModelState.IsValid check to OnPostAsync.
  2. Submit the form with an empty category. Confirm the page redisplays with a validation message instead of saving.
  3. Set a breakpoint right after the ModelState.IsValid check and inspect ModelState["NewSale.Category"].Errors in the debugger.

Change It

Add a second validation rule (for example [Range] on Amount) and confirm both a missing category and a negative amount are each individually caught and reported.

Hint

ModelState collects all validation failures from a single submission, not just the first one — inspect the whole collection, not one entry, when debugging a form that "isn't validating right".

Break It

Intentionally cause a runtime exception: call _dataAccess.InsertSale(null) or reference a property that doesn't exist on the model.

What happens & why

You'll get a NullReferenceException (or similar) and, in development, a detailed error page with a stack trace. Practice reading it bottom-up: find the first line in your code (not framework code) in the call stack — that's almost always where the real bug is, even if the exception is thrown deeper inside a library call. Undo the change once you've diagnosed it.

Explain It

Explain the difference between a validation failure (expected, handled by ModelState) and an unhandled exception (a bug), and how you'd diagnose each differently.

Lab 5

Complete CRUD Vertical Slice

Goal

Build list, create, edit, and delete for one entity, reinforcing the full request/data flow end to end.

Mental Model

List (OnGet)→ Create (OnPost)→ Edit (OnGet/OnPost)→ Delete (OnPost)

Short Explanation

A CRUD vertical slice is the same four operations you've already practiced individually, applied consistently to one entity: a list page (OnGet + a read DAL method), a create form (OnPostAsync + [BindProperty] + validation + an insert DAL method), an edit form (OnGetAsync(int id) to load, OnPostAsync to save, an update DAL method), and delete (a named OnPostDeleteAsync(int id) + a delete DAL method). Nothing new conceptually — the goal is fluency doing all four without step-by-step guidance.

Relevant Code

// Edit.cshtml.cs shape
public class EditModel : PageModel
{
    private readonly DataAccess _dataAccess;
    public EditModel(DataAccess dataAccess) => _dataAccess = dataAccess;

    [BindProperty]
    public SalesData Sale { get; set; }

    public IActionResult OnGet(int id)
    {
        Sale = _dataAccess.GetSaleById(id);
        if (Sale is null) return RedirectToPage("./Index");
        return Page();
    }

    public async Task<IActionResult> OnPostAsync(int id)
    {
        if (!ModelState.IsValid) return Page();
        _dataAccess.UpdateSale(id, Sale);
        return RedirectToPage("./Index");
    }
}

Run It

  1. Pick the Sales table (already backed by SalesData) or a new small table if you'd rather practice from scratch.
  2. Build Pages/Sales/Index.cshtml(.cs) (list), Create.cshtml(.cs), Edit.cshtml(.cs), and a delete handler off the list page.
  3. Add GetSaleById, UpdateSale, and confirm your Lab 3 InsertSale/DeleteSale are reused, not duplicated.
  4. Manually walk through: create a row, see it in the list, edit it, see the change persist, delete it, confirm it's gone.

Change It

Add server-side validation to the edit form that reuses the same annotations as create, and confirm invalid edits are rejected the same way invalid creates are.

Hint

If create and edit both bind to the same SalesData model, validation attributes only need to be defined once, on the model.

Break It

Delete a row, then click "Edit" using a stale link to that same (now-deleted) row's id.

What happens & why

If OnGet(int id) doesn't check for a missing record, you'll get a NullReferenceException when the page tries to render Sale.Category on a null Sale. This is why the "not found" redirect in the sample code above matters — always handle the "id doesn't exist anymore" case explicitly.

Explain It

Walk through, out loud or in writing, everything that happens between clicking "Edit" on a list row and seeing the save confirmation, including every SQL statement executed.

Lab 6

Realistic Sprint Ticket

Goal

Deliver a ticket from acceptance criteria only — no step-by-step instructions. Decide the shape of the change yourself.

Mental Model

Acceptance criteria→ Your design→ Implementation→ Verification

Short Explanation

Real tickets rarely specify the handler name, model shape, or SQL. This lab is intentionally under-specified: you decide the SQL, the handler(s), the model, the Razor markup, and any DAL/service changes. Use everything from Labs 1–5. If you get stuck, that's a signal to re-read a specific lab section, not to wait for instructions.

Ticket: Edit employee office location

Acceptance criteria:

  • Search employees by partial last name
  • Display matches
  • Select an employee
  • Edit their office location
  • Office location is required
  • Save the change to the database
  • Show validation errors when the save is rejected

Relevant Code

No sample solution is provided here on purpose. Reuse patterns from: search/filter (Lab 2's parameterized WHERE query), a select-and-edit flow (Lab 5's edit page), and required-field validation (Lab 4's data annotations). If an Employees table doesn't exist yet, add one the same way Sales is created in DataAccess.InitializeDatabase().

Run It

  1. Decide: one page with a search box and inline edit, or a search page plus a separate edit page? Either is valid — justify your choice.
  2. Write the SQL for the partial last-name search (LIKE with parameters) and the update statement.
  3. Build the handler(s), model, and DAL methods needed.
  4. Build the Razor markup for search results and the edit form.

Change It

Once it works, add a second search field (first name) without breaking the existing last-name search.

Hint

Consider whether your DAL method should take multiple optional parameters or whether two smaller methods are clearer. Either is defensible — the point is a deliberate choice, not a "correct" answer.

Break It

Try saving with an empty office location, and separately, try searching for a last name that matches nothing.

What happens & why

Both are expected states, not bugs: a required-field violation should show a validation message and redisplay the form (Lab 4 pattern); a no-results search should show an empty-state message, not an error. If either currently throws an exception or shows a blank page, that's the gap to fix.

Explain It

Explain your design choices to a teammate or reviewer: why this handler layout, why this SQL shape, and how validation errors surface to the user.
