Session 3

Backlogs, Work Items, and Refinement

Why it mattersLead prep: 45–60 minTeam session: 45–60 min
Why it matters: A board only helps when meaningful work is represented clearly enough to prioritize, discuss, review, and accept.

Backlog layers

The Product Backlog is the ordered list of desired product work. The Sprint Backlog is the selected work plus the plan for the current sprint. A Product Goal gives the longer direction; a Sprint Goal gives the near-term outcome.

TypeUseful forExample here
Epic / FeatureLarge outcome or capabilityCustomer account administration
StoryValuable slice of behaviorAllow an authorized user to update an account address
TaskImplementation stepUpdate .NET handler and database mapping
BugObserved defectUAT rejects an invalid date response
SpikeTime-boxed learningInvestigate a legacy integration constraint

Refinement and slicing

  • Clarify the user or operational outcome, acceptance criteria, and dependencies.
  • Split oversized work vertically so one slice can move through design, development, lead review, and UAT.
  • Track technical debt and sustainment work rather than hiding it in task notes.
  • A Definition of Ready can be a team convention, but it should not become a gate that delays useful conversation.

Facilitator guidance

Ask “What would a customer or operator be able to do when this is done?” before asking how many database, UI, or code changes are involved. Watch for horizontal slices such as “build the whole API” that cannot provide feedback until the end.

Questions to answer

  • When does a task belong on Azure Boards? Whenever meaningful work or risk needs visibility.
  • Who orders the Product Backlog? The Product Owner or business owner, informed by the team.
  • What if the item is unclear? Refine it, split it, or leave it out of Sprint Planning.

Learning objectives

  • Represent meaningful work in Azure Boards.
  • Write a useful item with outcome, acceptance criteria, and context.
  • Break large .NET, database, UI, and sustainment work into discussable slices.

Concept explanation: the board is the work conversation

Use the Product Backlog for everything that may matter; use the Sprint Backlog for the current two-week plan. A story can have tasks, but the story should still describe a valuable outcome. A bug, spike, or technical-debt item is valid work when it consumes team capacity.

Rule: If meaningful work is happening, represent it on the board.

Exercise: split and improve

  1. Rewrite “Improve the customer screen” as a user or operational outcome.
  2. Add acceptance criteria that UAT can verify.
  3. Split “upgrade the entire database and UI” into slices that can be reviewed.
  4. Choose whether each example is a story, task, bug, spike, or technical debt.

Key rules / facilitator questions

  • Does this item have a clear outcome?
  • Can someone else understand what acceptance means?
  • What dependency or design review needs to be visible?
  • Is this small enough to move across the board during one sprint?
