Team lead teaching guide

The six essential Scrum conversations

A concept-first reference for teaching the vital information developers need to absorb. Use the sections as a textbook, not as a script that must be delivered minute by minute.

How to use this guide: Teach the concepts in the order that makes sense for the team, use the local examples to make them concrete, and use the questions to check understanding. Each session remains a 45–60 minute lunch-and-learn, but the learning objective matters more than the clock.

Session 1: Agile, Scrum, and October 1

Core idea

Agile is a way of working that delivers useful increments, learns from feedback, and adapts when assumptions change. Scrum is the lightweight framework this team will use to make that work visible through a Product Backlog, Sprint Backlog, Sprint Goal, Daily Scrum, Sprint Review, and Retrospective.

What developers need to understand

  • October 1 formalizes backlog, board, and sprint tracking; it does not ask the team to stop doing design review, code review, UAT, or release governance.
  • The existing lifecycle, Design Review → Development → Code Review → UAT → Go Live, becomes part of a shorter and more visible Scrum flow.
  • A sprint is a two-week planning and learning cycle. It is not a promise that every request will be finished.
  • Transparency means the board shows what is planned, active, blocked, under review, accepted, or complete.
  • Inspection means the team looks at evidence during standups, reviews, and UAT. Adaptation means the plan changes openly when evidence requires it.

Local example

An enhancement to a customer workflow can be refined as a small backlog item, planned into a sprint, developed, submitted as a TFVC shelveset for Team Lead review, validated through UAT, marked Done, and released when operationally ready. Scrum shortens the feedback loop; it does not remove the controls.

Point to reinforce

Agile is not “no process.” It is a visible process that allows the team to learn before a large block of work reaches the end.

Check understanding

  • What changes on October 1, and what stays?
  • Why is a board item more useful than a verbal status update?
  • Where does our current design, review, UAT, or release work appear in the Scrum lifecycle?

Session 2: Roles, Responsibilities, and Ownership

Core idea

Scrum works when ownership is clear. Program governance and team execution are complementary layers: the program asks whether agreed outcomes are being delivered; the team asks how the work will be completed.

What developers need to understand

  • The Program Manager protects contract scope, deliverables, staffing/resources, risks, reporting, and formal contractor escalation.
  • The Government Lead / TPOC directs macro priorities within approved scope, reviews Epic and sprint progress, and confirms government expectations.
  • The Team Lead coordinates day-to-day execution, facilitates Scrum ceremonies, manages feature progress and board health, leads technical review, and escalates risks.
  • Developers own their User Stories and work items daily: estimates, implementation, ADO updates, blockers, refinement input, and early communication.
  • The customer or Product Owner voice clarifies value and acceptance. Developers decide how to implement within the approved objective.

Local decision rule

Do not begin an unapproved request because it came from a senior person or appears urgent. Add it to Azure DevOps, include the requestor, description, date, and estimate, have the Team Lead assess it, route it to the Government Lead, and record the decision before execution. Major efforts require epic-level review.

Point to reinforce

Facilitation is not command-and-control. A lead makes ownership and decisions visible, helps remove impediments, and coaches the team without becoming the only person who can move work forward.

Check understanding

  • Who decides priority within approved scope?
  • Who decides the technical implementation?
  • Who accepts completed work?
  • Where does a schedule, technical, scope, or dependency risk go?

Session 3: Backlogs, Work Items, Refinement, and Sprint Planning

Core idea

The backlog is the team’s shared decision space. Azure DevOps should make every meaningful request traceable, understandable, estimable, and reviewable before it becomes active work.

What developers need to understand

  • Use the hierarchy Epic → Feature → User Story / Work Item. An Epic represents a contract deliverable or program objective; a Feature represents a capability or planned release; a User Story or Work Item represents an enhancement, defect, technical task, or spike.
  • The Product Backlog contains possible work in priority order. The Sprint Backlog contains the work selected for the current two-week sprint and the team’s plan.
  • A useful item states an outcome, includes acceptance criteria, identifies dependencies, and names any design or validation work.
  • Refinement is where the team clarifies, splits, estimates, and exposes risk. A Definition of Ready may guide discussion, but it should not become a bureaucratic wall.
  • Vertical slices are preferable to “build the entire database/API/UI” because a slice can produce feedback and move through the workflow.

Local examples

“Fix dashboard filter” may be a defect. “Add MFA” may be a User Story under an authentication Feature. “Investigate a legacy integration constraint” may be a time-boxed spike. Database, .NET, UI, sustainment, technical debt, and design work all consume capacity and should be represented.

Point to reinforce

If meaningful work is happening, represent it on the board. Board accuracy is part of delivery, not end-of-sprint paperwork.

Check understanding

  • Can this item trace to an Epic or approved objective?
  • What will a customer or operator be able to do when it is complete?
  • Can UAT verify the acceptance criteria?
  • What would make this item too large or uncertain for one sprint?

Session 4: Estimation and Sprint Planning

Core idea

Planning creates a transparent forecast around a valuable Sprint Goal. Estimates express relative effort, complexity, and uncertainty; they are not hours, promises, or individual performance scores.

What developers need to understand

  • Use a simple scale such as 1, 2, 3, 5, 8, and 13. Compare an item to shared reference items rather than pretending the number is exact.
  • Plan from actual capacity: two teams of three developers, PTO, meetings, administration, support, sustainment bugs, and known dependencies.
  • Use the program’s starting allocation as a planning constraint: 50% major work, 25% minor work, and 25% meetings and administration.
  • Velocity is a team trend that can inform a forecast. It must never become a target used to rank developers.
  • Unfinished work is visible and returned for re-prioritization; it is not silently counted as complete.

When urgent work arrives

Create or locate the Azure DevOps work item, clarify urgency and scope, estimate the impact, and make the tradeoff visible. The team may change the forecast or Sprint Goal, but it should not hide the work or pretend capacity was unlimited.

Point to reinforce

Protect the outcome, adapt the task list. The Sprint Goal gives the team a reason to negotiate scope when reality changes.

Check understanding

  • What is our Sprint Goal?
  • What capacity is actually available after the 50/25/25 allocation, PTO, and support?
  • Which item needs splitting before planning?
  • What will change if an urgent production bug consumes two days?

Session 5: Running the Sprint and Daily Scrum

Core idea

The Daily Scrum is a short team coordination conversation about progress toward the Sprint Goal. It is not a management status report, a performance evaluation, or a detailed troubleshooting meeting.

What developers need to understand

  • Use Azure Boards as the visual source of truth and update assigned work every business day.
  • Walk work from right to left: finish existing work before starting more whenever possible.
  • Describe the item, its current state, its next state, what threatens the goal, and what collaboration is needed.
  • Document blockers in the work item the same day they are identified. Escalate schedule, technical, scope, and dependency risks immediately.
  • An item In Progress for more than five business days without an update is an aging signal for Team Lead escalation.
  • Park deep technical discussions with a named owner and follow-up time after standup.

Useful language

Replace “I worked on the screen” with “The address-validation item is In Progress, the database mapping is ready for review, and I need the UAT owner to confirm the invalid-date case.”

Point to reinforce

Early communication gives the team options; late communication creates emergencies. The board should answer what is active, blocked, complete, and next without a separate explanation.

Check understanding

  • Which item moved?
  • What is the next state?
  • What threatens the Sprint Goal?
  • Who owns the next action on the blocker?

Session 6: Quality Flow, Sprint Closeout, and Full Simulation

Core idea

Work is not Done because coding stopped. It is Done when the agreed quality, review, acceptance, tracking, and validation evidence exists.

What developers need to understand

Use this workflow:

Work Item→In Progress→TFVC Shelveset→Team Lead Review→Check-in→UAT→Done
  • Associate every change with its Azure DevOps work item.
  • Create a TFVC shelveset for Team Lead review before check-in. This is not a Git pull request workflow.
  • Address review feedback, complete the correct TFVC check-in, and provide build and validation evidence.
  • Complete UAT where required. If UAT rejects the item, it remains out of Done and the acceptance gap is recorded.
  • Use the Definition of Done: acceptance criteria, code complete, work-item association, lead review, correct check-in, application build, required validation, UAT where applicable, and accurate board status. Unit tests and CI are future maturity goals, not current gates.

Closeout concepts

  • Sprint Review: demonstrate the completed increment and gather feedback.
  • Release / Go Live: may happen independently of the sprint boundary when operationally ready.
  • Retrospective: ask what worked, what did not, and what to change; choose only one or two actions.

Point to reinforce

Make quality and tradeoffs visible. When a story grows, a production issue arrives, a dependency blocks work, or UAT rejects functionality, adapt the plan openly and inspect the system before blaming a person.

Check understanding

  • What evidence is required before Done?
  • Where does TFVC shelveset review occur?
  • What is the difference between Sprint Review and UAT?
  • What improvement will we actually try next sprint?
Lead closeout: Ask developers to explain one work item from Epic or Feature through Azure Boards, TFVC shelveset review, UAT, Done, and release. Then ask each person to name one behavior they will use on October 1.
