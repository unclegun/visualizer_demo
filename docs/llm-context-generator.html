What the script does

The generator starts from a project directory, auto-discovers the solution root by walking up until it finds the nearest parent folder that contains a .sln file, and then builds an incremental context pack under llm-context/. Only files that match .llmwhitelist and do not match .llmignore are eligible for inclusion.

Workflow in practice

  1. 1. Resolve the solution root from the current project path.
  2. 2. Load appsettings.llmcontext.json, .llmwhitelist, and .llmignore.
  3. 3. Reuse cached fragments and cached summaries when file size, timestamp, or hash has not changed.
  4. 4. Regenerate only the changed fragment and summary files, then rebuild the final output text files only if their content actually changed.
Why this design works: it gives a large language model a stable, copyable context artifact without turning every normal build into a full semantic analysis pass.

Why it uses two output files

solution-index.txt

The fast catalog file. It lists the files that passed the filters and gives a compact, human-readable summary for each one.

  • Quick to diff and cheap to inspect.
  • Useful when you want a map of the solution before pulling in raw content.
  • Regenerated only when the resulting index text actually changes.

solution-context.txt

The prompt-ready file. It contains trimmed fragments and shallow summaries until the configured context budget is reached.

  • Optimized for pasteability into LLM workflows.
  • Keeps raw code and summary text together.
  • Also written only when the generated content actually changed.
A single file would force the same artifact to serve two jobs: quick indexing and prompt payload generation. Splitting them keeps each output easier to diff, smaller to inspect, and cheaper to reuse.

How .llmwhitelist and .llmignore work

The generator uses a positive filter first and a subtractive filter second. Files are only considered when they match at least one whitelist pattern and do not match any ignore pattern. That keeps the input set explicit, predictable, and easy to tune for large solutions.

Whitelist

Include the file types that matter to Razor Pages and DAL understanding: PageModels, Razor markup, SQL, JSON settings, project metadata, and any narrowly scoped extras your team actually wants in context.

Ignore

Strip out build output, generated files, vendor assets, migration churn, and anything else that adds bytes without adding decision-making value.

How appsettings.llmcontext.json controls the build

          
The settings file governs output location, file-size trimming, context budget, summary budget, and whether frontend files should receive summaries. In other words, it defines how aggressive the build step should be and how much context the final artifact is allowed to carry.

          

            

              
                

                  Setting
                  Purpose
                

              
              
                
OutputDirectoryLocation of solution-index.txt, solution-context.txt, and the cache folders.

                
MaxFileBytesUpper bound for the raw content fragment taken from any single file.

                
SoftContextBytesBudget for the combined prompt-ready context file before the generator stops adding more fragments.

                
MaxSummaryFileBytesCap for each summary text file so summaries stay compact.

                
EnableFrontendSummariesControls whether JavaScript, TypeScript, CSS, and related frontend files receive summary generation.

How the incremental cache works

          
The cache is intentionally simple. The manifest remembers relative path, file size, last write time, and hash. If the metadata matches and the cached text artifacts still exist, the script reuses them. If metadata changed, it hashes the file. If the hash still matches, it still reuses the existing fragment and summary. Only truly changed inputs get re-read and re-summarized.

          

            This is intentionally a build-friendly optimization, not a perfect source-of-truth database. The goal is to avoid repeatedly summarizing hundreds of unchanged files during ordinary local builds.
          

          

            
Reused when unchanged
Cached fragments and summaries are reused to minimize file reads, summary generation, and output churn.

            
Outputs stay stable
The final solution-index.txt and solution-context.txt are only written when the content actually differs, which keeps diffs quieter in CI and local repos.

          

        


        

          
Razor Pages + DAL detection

          
This summary pass is intentionally shallow and regex-based for speed. It is not trying to build a Roslyn symbol graph. Instead, it extracts just enough signal to make the generated index and context useful for Razor Pages teams.

          

            
@page and @model detection
For .cshtml files, the generator looks for @page to distinguish full Razor Pages from partial fragments and captures the @model type when present.

            
PageModel handler extraction
For .cshtml.cs files, it identifies the PageModel class and extracts handler names such as OnGet, OnGetAsync, OnPostSaveAsync, and similar variations.

            
DAL class and method summaries
C# files in DAL-like folders or classes ending in names such as Dal, Repository, Queries, or Commands get DAL-oriented summaries and a shallow public method list.

            
SQL operation hints
The pass scans for SQL verbs like SELECT, INSERT, UPDATE, DELETE, MERGE, and EXEC so the index can hint at read/write behavior.

          

          

            Table schema generation is intentionally out of scope here. If your team needs schema-level context, keep that in a separate script so this build hook stays lightweight.
          

        


        

          
Architecture layout

          

            
solution-index.txt
The compact solution map. Good for quick review, diffs, and file-level scanning before loading larger prompt context.

            
solution-context.txt
The prompt payload. Contains trimmed source fragments plus summaries until the soft byte budget is reached.

            
llm-context/.cache/fragments
One cached prompt fragment per file. These are reused when the source file did not meaningfully change.

            
llm-context/.cache/summaries
Compact summary text files for each eligible source file, kept separate so summaries can be reused independently.

            
llm-context/.cache/manifest.json
The change-detection ledger. It records relative paths, size, last-write ticks, hash, and cache file names so the generator can cheaply determine when cached artifacts are safe to reuse.

          

        


        

          
How to wire the script into a .csproj build target

          
Use a small target that runs before the normal build, skips design-time builds, and can be disabled through an MSBuild property. The sample below assumes you eventually copy the script into a real solution under tools/Generate-LlmContext.ps1.

          

            
.csproj build target snippet

            


<PropertyGroup>
  <GenerateLlmContext>true</GenerateLlmContext>
</PropertyGroup>

<Target Name="GenerateLlmContext"
        BeforeTargets="BeforeBuild"
        Condition="'$(DesignTimeBuild)' != 'true' and '$(GenerateLlmContext)' == 'true'">
  <Exec Command='pwsh -NoProfile -ExecutionPolicy Bypass -File "$(SolutionDir)tools\Generate-LlmContext.ps1" -ProjectPath "$(MSBuildProjectDirectory)"' />
</Target>

            

          

          

            Skipping design-time builds matters. It avoids running the generator during IntelliSense-triggered builds in Visual Studio or other IDE workflows where the context artifacts are not the primary concern.
          

        


        

          
Performance considerations

          
    
            
  • The generator avoids Roslyn because full semantic analysis would add unnecessary overhead to a build-oriented documentation artifact.
    • 
            
  • Whitelist-first filtering reduces the candidate set before any summary work happens.
    • 
            
  • Cache reuse minimizes repeated fragment generation and summary generation for unchanged files.
    • 
            
  • Final outputs are only rewritten when the generated content changed, which reduces disk churn and noisy diffs.
    • 
            
  • Frontend summaries are configurable so teams can keep the focus on Razor Pages, PageModels, DAL, and SQL-heavy files.
    • 
          

          

            This approach avoids slowing builds too much because it uses simple regex extraction, capped fragment sizes, and manifest-driven reuse instead of parsing the entire solution into a rich semantic model on every build.
          

        


        

          
Practical tuning

          

            
MaxFileBytes
Raise it when important PageModels or DAL files are getting cut off too early. Lower it when a few large files dominate the prompt budget.

            
SoftContextBytes
Increase it if your LLM tooling can handle larger prompt payloads. Decrease it when you want smaller, more diffable context packs.

            
MaxSummaryFileBytes
Keep this small so the index stays signal-heavy. If summaries become verbose, trim this before trimming the raw code fragments.

            
Disable frontend summaries
Do this when your main goal is backend workflow understanding and the frontend files are mostly static, generated, or incidental to the PageModel and DAL flow.

          

        


        

          
Recommended repo layout

          
For the demo site, the script lives under docs/examples/llm-context/ so it is easy to browse and copy. In a real Razor Pages solution, move the script into a dedicated tools/ folder at the solution root and keep the control files beside the .sln.

            Keeping the control files at the solution root matches the script's auto-discovery behavior and makes the generator consistent no matter which project directory launches it.
          

        


        

          
Recommended default settings and customization

          
    
            
  • Start with Razor Pages, C#, SQL, JSON, and project files only. Add more only when they materially improve prompt quality.
    • 
            
  • Ignore build output, generated code, minified assets, migrations, and vendor folders by default.
    • 
            
  • Leave frontend summaries disabled unless your prompts regularly need to reason about JavaScript- or CSS-driven behavior.
    • 
            
  • Keep schema generation in a separate step so the context build remains fast and focused.
    • 
          

          

            

              
Customization guidance

              Change the control files before changing the script.
            

            
Use .llmwhitelist to add solution-specific patterns such as stored procedure folders, API contracts, or DTO libraries. Use .llmignore to cut out heavy but low-value content such as snapshots, generated artifacts, or bulky static assets.

            
If your DAL layer lives in a nonstandard folder, keep the script simple and rename folders or add clear class suffixes before expanding the regex rules. That keeps the build hook maintainable.
